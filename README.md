**Music Store Analysis** is an end-to-end **SQL Data Analytics project** built around a relational music-store database.

The project takes structured transactional and catalogue data and uses SQL to investigate business questions related to:

**Customer Spending • Sales Performance • Music Preferences • Artists • Genres • Revenue • Geographic Demand**

The analytical workflow is:

<p align="center">

**UNDERSTAND THE DATA**  
↓  
**ASK BUSINESS QUESTIONS**  
↓  
**QUERY THE DATABASE**  
↓  
**ANALYZE THE RESULTS**  
↓  
**EXTRACT BUSINESS INSIGHTS**

</p>

# 💡 WHAT DOES THIS PROJECT ACTUALLY DO?

Imagine a digital music store containing information about thousands of:

**Customers • Invoices • Tracks • Albums • Artists • Genres • Employees • Playlists**

The database contains the information, but business questions require analysis.

For example:

> 🎯 **Who spends the most?**

> 💰 **Which customers contribute the most revenue?**

> 🎵 **Which genres are most popular?**

> 🎸 **Which artists have the largest number of tracks?**

> 🌍 **Which countries generate the most purchasing activity?**

> 👤 **Who is the highest-spending customer in each country?**

This project uses **SQL as the analytical layer** between the raw relational data and these business questions.

🧠 SQL CONCEPTS USED
01 — Fundamental SQL
SELECT
FROM
WHERE
ORDER BY
GROUP BY
DISTINCT
LIMIT

These operations form the foundation for retrieving and filtering information from the database.

02 — Aggregate Functions
COUNT()
SUM()
AVG()
MIN()
MAX()

Aggregations allow raw records to be converted into measurable metrics.

For example:

SELECT
    country,
    SUM(total) AS revenue
FROM invoice
GROUP BY country;
03 — JOINs

JOINs connect information distributed across different relational tables.

SELECT
    c.first_name,
    c.last_name,
    i.total
FROM customer c
JOIN invoice i
    ON c.customer_id = i.customer_id;

This type of relationship makes it possible to connect customer information with purchasing information.

🧩 SUBQUERIES

Subqueries are used when one analytical result becomes an input to another query.

They are useful for questions such as:

Customers spending above an average value
Tracks longer than the average duration
Comparing individual values against calculated benchmarks
Filtering results based on another query

Conceptually:

                MAIN QUESTION
                     │
                     ▼
                SUBQUERY
                     │
                     ▼
              CALCULATED VALUE
                     │
                     ▼
              FINAL RESULT
🏗️ COMMON TABLE EXPRESSIONS

CTEs provide a structured way to break complicated SQL analysis into readable stages.

WITH customer_sales AS
(
    SELECT
        customer_id,
        SUM(total) AS total_spent
    FROM invoice
    GROUP BY customer_id
)

SELECT *
FROM customer_sales;

CTEs are particularly useful when analytical logic involves multiple stages.

🪟 WINDOW FUNCTIONS

Window functions allow calculations to be performed across related rows while preserving row-level information.

Examples include:

ROW_NUMBER()
RANK()
DENSE_RANK()
SUM() OVER()
AVG() OVER()

They are useful for:

Ranking customers
Comparing customers
Country-level rankings
Running totals
Comparative analysis
